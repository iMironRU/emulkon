# Эмулятор подключаемого оборудования для 1С (БПО): архитектура

Название: **Эмулкон** (до версии 0.2.0 — «Эмукон»).
Статус документа: черновик v0.1 для старта разработки в Claude Code.

---

## 1. Цель

Дать разработчикам и тестировщикам 1С возможность работать с торговым оборудованием (ККТ, эквайринг, весы, сканеры и др.) без реального железа. Эмулятор подключается к «1С:Библиотеке подключаемого оборудования» (БПО) так же, как настоящий драйвер, поэтому прикладной код 1С не знает, что оборудование виртуальное.

Ключевые свойства:

- Вся логика и состояние устройств живут на **центральном сервере**.
- Клиентская часть (драйвер) **тонкая**: переправляет вызовы на сервер по HTTP и поднимает события от сервера в 1С.
- Сервер имеет **веб-интерфейс** для настройки и ручного управления эмуляцией.
- **Удалённая работа**: RDP, терминальные серверы, тестировщики на других машинах, CI.
- **Сквозное логирование** всех обменов.
- **Внедрение сбоев** и сценарии, которые трудно воспроизвести на реальном железе.

### Что не входит в цель (non-goals)

- Эмуляция протоколов производителей (ESC/POS, протоколы Атол/Штрих по COM или TCP) на первом этапе. Архитектура должна позволять добавить это позже адаптерами, но в v1 этого нет.
- Проверка настоящих драйверов производителей.
- Замена боевых ОФД, «Честного знака», ЕГАИС (отдельный набор эмуляторов, см. раздел 12).

## 2. Контекст: как устроена БПО (что нужно подтвердить)

Это отправная точка. Часть утверждений нужно **проверить по первоисточникам** до начала реализации компоненты (см. раздел 13).

Подтверждено поиском:

- Современные драйверы БПО реализуются как **внешние компоненты по технологии Native API** и соответствуют документу «Требования к разработке драйверов подключаемого оборудования» (в источниках упоминаются версии 2.4, 3.0, 3.2, 3.5). Это касается и драйверов самой 1С (сканеры, весы, принтер чеков, дисплей покупателя), и партнёрских (Рарус и др.).
- Старые обработчики драйверов на встроенном языке 1С оставлены только ради обратной совместимости. Макеты с драйверами в новые версии библиотеки не включаются.
- Следовательно, **вариант «эмулятор без внешней компоненты, только код 1С» не работает**. Нужна компонента Native API.

Нужно уточнить (не подтверждено):

- Точный набор методов и событий компоненты для каждого типа оборудования в версии требований 3.x.
- Как БПО регистрирует и выбирает драйвер (манифест, описание драйвера, идентификаторы, привязка к типу оборудования).
- Остался ли в актуальной БПО промежуточный слой на 1С между прикладным кодом и компонентой, и что он делает.
- Поведение компоненты в веб-клиенте и на Linux.

## 3. Общая схема

```
┌────────────────────────── Рабочее место / сервер приложений 1С ─────────────────────────┐
│                                                                                          │
│  Прикладной код 1С ──► БПО (МенеджерОборудования...) ──► Компонента-драйвер (Native API) │
│                                                              │   ▲                        │
└──────────────────────────────────────────────────────────────┼───┼────────────────────────┘
                                                  HTTP (команды)│   │ SSE/WebSocket (события)
                                                               ▼   │
┌──────────────────────────────────── Сервер эмуляции ────────────────────────────────────┐
│  Device API ──► Диспетчер сессий ──► Модели устройств (конечные автоматы)               │
│                          │                    ▲                                          │
│                          ▼                    │                                          │
│                  Движок сценариев и внедрения сбоев                                      │
│                          │                                                               │
│                          ▼                                                               │
│                  Журнал обменов (append-only)  ◄──── Control API ◄──── Веб-UI / автотесты│
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

Три границы:

1. **1С ↔ компонента**: контракт БПО (требования к драйверам). Мы его не меняем, только реализуем.
2. **Компонента ↔ сервер**: наш протокол (Device API). Простой, версионируемый, без бизнес-логики на клиенте.
3. **Человек и автотесты ↔ сервер**: Control API и веб-UI.

## 4. Компоненты системы

### 4.1. Компонента-драйвер (клиентская часть)

Назначение: быть «настоящим драйвером» с точки зрения БПО, а внутри просто прокси.

Обязанности:

- Реализовать интерфейс Native API по требованиям БПО выбранной версии.
- На каждый вызов метода от 1С: сформировать HTTP-запрос к серверу, дождаться ответа (с таймаутом, который задаёт сервер или настройка), вернуть результат в формате, ожидаемом БПО.
- Держать **фоновое соединение** с сервером (WebSocket или SSE) для событий и при их приходе поднимать внешнее событие в 1С штатным механизмом Native API.
- Переподключаться с экспоненциальной паузой, не блокировать поток 1С.
- Хранить минимум настроек: адрес сервера, токен устройства, идентификатор рабочего места, параметры TLS.
- Явно отображать, что это эмулятор (название драйвера, описание, версия, предупреждение в результате тестирования устройства).

Решения по реализации:

- Язык: **C++17** (по SDK Native API).
- HTTP: без внешних библиотек — WinHTTP на Windows, свой клиент HTTP/1.1 на сокетах на Linux (решение 2026-10-15); события — SSE.
- Платформы: **Windows x64 и x86**, **Linux x64**. Android рассматривать после v1.
- Одна кодовая база, один бинарный артефакт на платформу. Тип устройства определяется описанием драйвера и настройками, а не отдельным кодом.
- Упаковка: ZIP с манифестом по правилам 1С для внешних компонент и драйверов. Детали проверить.

**Принцип**: клиент не знает ничего про ККТ, банки и весы. Он знает только «метод, параметры, ответ, событие».

### 4.2. Сервер эмуляции

Состав:

| Модуль | Ответственность |
|---|---|
| Device API | Приём команд от компонент, раздача событий |
| Диспетчер сессий | Привязка рабочее место → виртуальное устройство, токены, общие устройства |
| Модели устройств | Конечные автоматы ККТ, эквайринга, весов, сканера и др. |
| Движок сценариев | Правила «если пришла команда X при условии Y, сделать Z» |
| Внедрение сбоев | Задержки, ошибки, обрывы, ответ после таймаута, дубли |
| Журнал | Неизменяемый поток событий обмена |
| Control API | Управление состоянием и сценариями извне (UI, автотесты) |
| Веб-UI | Интерфейс над Control API |

Рекомендации по стеку (обсуждаемо, решение за владельцем проекта):

- Язык сервера: **Go** (один бинарник, простой Docker, хорошая модель для WebSocket/SSE и таймеров) или TypeScript. По умолчанию в документе принят Go.
- Хранилище: **без традиционной СУБД**. Журнал и конфигурация как append-only файлы (JSONL) плюс снимки состояния в памяти. Конфигурация профилей и сценариев в файлах YAML, пригодных для хранения в git.
- Веб-UI: лёгкий SPA, отдаваемый самим сервером (встроенная статика).
- Развёртывание: **Docker-образ**, подходит для Coolify и для запуска в CI.

### 4.3. Учёт устройств (решение 2026-10-09)

**Что драйвер знает об экземпляре.** БПО передаёт драйверу при подключении только тип оборудования
и параметры `P_*`, сохранённые в карточке экземпляра «Подключаемого оборудования»
(`МенеджерОборудования.ПолучитьПараметрыXML`, БПО 3.2.9). Ссылки на экземпляр, его наименования,
организации, рабочего места БПО и базы среди них нет. Поэтому драйвер сам заводит параметры
экземпляра, а БПО их хранит:

- **`InstanceID`** — идентификатор экземпляра. В описании настроек драйвер отдаёт его
  `DefaultValue` новым GUID при каждом запросе. Форма «Настройка» БПО подставляет значение по
  умолчанию, если его нет, и сохраняет при «ОК». Так каждый экземпляр после первой настройки
  получает свой идентификатор, и две ККТ одной базы (разные отделы, юрлица) — два устройства;
- **`Infobase`** — база 1С, **`InstanceName`** — наименование экземпляра в 1С. Их заполняет
  обработка-помощник (бэклог) или человек. Пустую «Базу 1С» драйвер берёт из командной строки
  процесса 1С: `/F"путь"`, `/S"сервер\база"`, `/IBName`, `/IBConnectionString` (остальные ключи,
  в том числе `/P` с паролем, не читаются).

Параметры «только для чтения» форма БПО не сохраняет, поэтому это обычные параметры в группе
«Экземпляр (заполняет Эмулкон)».

**Ключ устройства** — `InstanceID` и тип, если идентификатор пришёл. Иначе — рабочее место и тип,
как раньше; такое устройство помечается «не настроено». Если в одном процессе 1С один
`InstanceID` подключён дважды (экземпляр скопировали вместе с параметрами), драйвер шлёт
признак копии, и сервер заводит отдельное устройство с пометкой «копия».

**Ничего не удаляется само.** Устройство, которое давно не подключалось, получает пометку (как
в личном кабинете ОФД); удалить его можно только руками.

**Хранение.** Устройства, рабочие места, их подписи, настройки устройств и настройки классов по
умолчанию сохраняются в каталоге данных (`registry.json`) и переживают перезапуск. Настройки — это
часть ключей состояния модели, описанная схемой (`docs/protocol.md` §2.3): режим карты, ширина
ленты, предел весов… Сбои и текущее состояние (бумага, крышка, связь, вес) правятся, но не
сохраняются: полное состояние моделей (смена, ФН, пакет терминала) живёт в памяти, как раньше.
Новое устройство получает настройки своего класса; «Сброс» возвращает модель к её настройкам.

**Вывод документов на рабочем месте — настройка устройства (решение 2026-10-09).** Показывать
ли чек на экране кассы, печатать ли на принтер Windows, какой принтер и какие документы — это
настраивается в карточке устройства, а не в меню трея. Сервер хранит настройку у устройства и
кладёт решение в запись журнала `device.print` (`output`); трей только выполняет его и сообщает
серверу принтеры своего компьютера. «Напечатать последний документ» — кнопка в карточке:
сервер пишет `device.reprint`, трей печатает. В трее остаются настройки самого трея и сервера:
адрес, токен, рабочее место, запуск сервера.

## 5. Протокол компонента и сервера (Device API)

> **Актуальный протокол — [docs/protocol.md](docs/protocol.md) и [docs/openapi.yaml](docs/openapi.yaml).**
> Решение 2026-10-08 по итогам изучения требований к драйверам 4.8: параметры методов
> позиционные (массив туда и обратно, `result` — возвращаемое значение), тип устройства —
> `equipment_type` из таблицы требований, методы до `ConnectEquipment` компонента обслуживает
> сама. Ниже — исходный набросок.

Версионирование: префикс `/api/v1`. Формат: JSON, UTF-8.

### 5.1. Сессия

```
POST /api/v1/sessions
{
  "workstation_id": "KASSA-01",
  "device_token": "…",
  "driver_type": "kkt|acquiring|scales|scanner|printer|display|…",
  "driver_version": "x.y.z",
  "bpo_requirements_version": "3.5"
}
→ 200 { "session_id": "…", "device_id": "…", "limits": { "default_timeout_ms": 30000 } }
```

### 5.2. Команда

```
POST /api/v1/devices/{device_id}/commands
{
  "request_id": "uuid",            // идемпотентность
  "method": "…",                   // имя метода из контракта БПО
  "params": { … },                 // параметры как в контракте
  "client_ts": "2026-…Z"
}
→ 200 {
  "request_id": "uuid",
  "result": true,
  "output": { … },                 // выходные параметры метода
  "error_code": 0,
  "error_text": ""
}
```

Правила:

- Повтор запроса с тем же `request_id` возвращает тот же результат (идемпотентность). Это важно для сценария «ответ пришёл после таймаута».
- Сервер может намеренно задержать ответ. Таймаут компоненты задаётся настройкой драйвера, сервер лишь сообщает рекомендуемое значение.

### 5.3. События (сервер → компонента)

Канал: SSE `/api/v1/devices/{device_id}/events` (решено: проще на WinHTTP, проходит через прокси; подробно — docs/protocol.md §1.4). Подтверждение — курсором `Last-Event-ID`, отдельного `ack` нет.

```
{ "event_id": "…", "type": "…", "data": { … } }
```

События: сканирование штрихкода, считывание карты, стабилизация веса, нажатие кнопки, изменение статуса устройства. Компонента подтверждает получение (`ack`) и поднимает событие в 1С.

### 5.4. Служебное

- `GET /api/v1/health`
- `GET /api/v1/devices/{device_id}/description`: описание драйвера для БПО (параметры, поддерживаемые команды).

Точные имена методов, структура параметров и описание драйвера **определяются документом требований БПО** (см. раздел 13), а не придумываются здесь.

## 6. Модели устройств

Каждая модель это конечный автомат плюс набор параметров, который меняют сценарии и оператор в UI.

### 6.1. ККТ (приоритет 1)

Состояния: `нет_смены`, `смена_открыта`, `смена_истекла (>24ч)`, `чек_открыт`, `ошибка`.

Операции: открытие и закрытие смены, X- и Z-отчёты, чек прихода и возврата, чек коррекции, внесение и выплата, печать нефискального документа, получение состояния и фискальных данных.

Сценарии ошибок: нет бумаги, крышка открыта, ФН заполнен, ФН требует замены, нет связи с ОФД (рост очереди неотправленных документов), смена больше 24 часов, неверные реквизиты, ошибка маркировки (КМ).

Параметры: поддерживаемые версии ФФД (1.05, 1.2), система налогообложения, модель (профиль), задержка печати.

Результат: фискальные признаки (ФД, ФП, номер ФН, QR) и «напечатанный» чек в виде текста и картинки для просмотра в UI.

### 6.2. Эквайринг (приоритет 2)

Операции: оплата, возврат, отмена, сверка итогов, оплата по СБП (QR), получение слипа.

Сценарии: отказ банка, таймаут, обрыв на середине операции, неверный ПИН, зависшая операция, **неоднозначный результат** (деньги списаны, ответа нет), ответ после таймаута.

### 6.3. Весы (приоритет 3)

Простые весы: стабильный и нестабильный вес, тара, ноль, перегруз, потеря связи, события «вес стабилизировался».
Весы с печатью этикеток: загрузка PLU, формирование этикетки, весовые штрихкоды.

### 6.4. Сканер (приоритет 4)

Это в первую очередь **генератор событий**: EAN-13, EAN-8, Code128, весовые коды, GS1 DataMatrix (с разделителями GS), искажённые коды, пакетная «стрельба». Управляется из UI и Control API.

### 6.5. Дальше (плагины)

Принтеры чеков и этикеток (рендер напечатанного), дисплей покупателя (визуализация), ТСД, денежный ящик, считыватели карт. Каждый тип добавляется как модуль модели без изменения ядра.

### 6.6. Профили моделей

Набор параметров, имитирующий конкретную модель производителя: коды ошибок, тексты, лимиты, задержки. Профили хранятся как файлы YAML.

## 7. Движок сценариев и внедрение сбоев

Правило сценария:

```yaml
- name: "Банк отказывает на третьей оплате"
  match:
    device: acquiring-01
    method: Pay
    nth_call: 3
  action:
    type: respond
    result: false
    error_code: 51
    error_text: "Недостаточно средств"
    delay_ms: 2500
```

Типы действий: `respond`, `delay`, `error`, `drop` (соединение оборвано), `respond_after_timeout` (ответить после таймаута клиента), `duplicate` (повторное сообщение), `set_state` (изменить состояние модели), `emit_event`.

Условия: по устройству, методу, значению параметра, номеру вызова, вероятности, времени, состоянию модели.

Требования:

- Сценарии включаются и выключаются на лету, без перезапуска.
- Все сработавшие правила попадают в журнал (чтобы было видно, что ответ «искусственный»).
- Сценарии хранятся в файлах и пригодны для версионирования в git.

**Реализовано (2026-10-09, решение):**
- Формат — **JSON** (`<каталог данных>/scenarios.json`), а не YAML: сервер обходится стандартной
  библиотекой. YAML добавим, если понадобится импорт из git с комментариями.
- Действия: `error` (ответ ошибкой устройства, модель не вызывается, её же вернёт GetLastError),
  `delay`, `drop` (команда выполнена, соединение оборвано — повтор с тем же request_id получает
  сохранённый ответ), `late` (ответ после задержки — после таймаута компоненты), `set_state`,
  `emit_event`. `duplicate` не делаем: повтор запроса — забота компоненты, его проверяет `drop`.
- Условия: устройство, класс, рабочее место, метод (несколько через запятую), параметр по номеру
  (`equals`/`contains`), `nth_call`, `every`, `probability`, `limit` срабатываний. Время и состояние
  модели — позже.
- Правило вычисляется один раз на первое выполнение команды; срабатывания — в `applied_rules`
  записей журнала. Счётчики (`seen`, `fired`) обнуляет `POST /control/v1/reset`.
- Простые исходы терминала без правил — копейки суммы, порог, тестовые карты (docs/models/acquiring.md).

## 8. Журнал

Каждая запись:

```json
{
  "ts": "…",
  "correlation_id": "…",
  "workstation_id": "KASSA-01",
  "device_id": "kkt-01",
  "direction": "in|out|event",
  "method": "…",
  "payload": { … },
  "latency_ms": 123,

```

Свойства:

- Append-only, неизменяемый (подход event sourcing: состояние моделей должно быть восстановимо из журнала).
- Просмотр в UI с фильтрами, поиск, экспорт.
- Возможность **воспроизвести сессию** для автотеста.
- Ротация и ограничение размера.

## 9. Control API и веб-UI

### 9.1. Control API (для автотестов, например Vanessa, и для UI)

Примеры (окончательные имена уточнить при реализации):

- `GET /control/v1/devices`: список устройств и состояния.
- `PUT /control/v1/devices/{id}/state`: задать состояние (вес, статус бумаги, остаток в ФН).
- `POST /control/v1/devices/{id}/events`: сгенерировать событие (сканирование, поднесение карты).
- `POST /control/v1/scenarios` / `DELETE …`: управление сценариями.
- `GET /control/v1/journal?...`: чтение журнала.
- `POST /control/v1/reset`: сброс состояния перед тестом.

Control API защищён отдельным токеном (не тем, что у компоненты).

### 9.2. Веб-UI

Экраны:

1. **Устройства**: классы → экземпляры (база, рабочее место, наименование в 1С, онлайн, пометки), карточка с настройками в виде формы, состоянием в реальном времени и быстрыми действиями («положить вес», «поднести товар», «отказать в оплате», «закончить бумагу»). Там же **классы**: настройки по умолчанию для типа (§4.3).
2. **Сценарии**: редактор и включение.
3. **Журнал**: поток обменов в реальном времени.
4. **Просмотр печати**: что «напечаталось» на ККТ и принтере, слип эквайринга, дисплей покупателя.
5. **Рабочие места**: подпись, базы, устройства, сессии, токены; позже — пульт на телефоне.
6. **Настройки**: профили моделей, токены, ретенция журнала.

## 10. Безопасность и защита от попадания в прод

- Токены устройств и отдельный токен Control API. Токен рабочего места называет место сам
  и защищает его от подключений без токена (docs/protocol.md §1.1).
- TLS для не-локальных развёртываний.
- Драйвер **визуально отличим** от боевого: в названии «ЭМУЛЯТОР», в описании предупреждение, при тесте устройства выводится явное сообщение, чеки и слипы помечены как тестовые.
- В журнале отдельно фиксируются подключения с неизвестных рабочих мест.
- Данные, похожие на персональные или платёжные, не используются: эмулятор работает только с тестовыми данными, реальные номера карт и ПИН не принимаются.

## 11. Развёртывание

- Docker-образ сервера, конфигурация через переменные окружения и каталог данных.
- Варианты: локально у разработчика, общий тестовый стенд (например, через Coolify), контейнер в CI.
- Компонента устанавливается на рабочие места так же, как обычный драйвер БПО (архив драйвера), и настраивается адресом сервера.

## 12. Дальнейшие эмуляторы (за рамками v1)

- Эмулятор ОФД и ФНС (приём чеков, задержки, отказы).
- Эмулятор «Честного знака» и УТМ ЕГАИС (проверка КМ, статусы, ошибки).
- Адаптеры протокольного уровня (виртуальный COM, TCP-ККТ), чтобы проверять настоящие драйверы производителей. Подключаются к тому же ядру сервера.
- Терминалы самообслуживания (комбинация нескольких устройств в одной сессии).

## 13. Открытые вопросы и первые исследовательские задачи

Эти пункты нужно закрыть **до** реализации компоненты:

1. Получить и изучить актуальный документ «Требования к разработке драйверов подключаемого оборудования» (версия 3.x) на ITS (раздел методической поддержки разработчиков 1С). Он может требовать авторизации, тогда запросить текст у владельца проекта.
2. Выписать для каждого типа оборудования обязательные методы, их параметры, формат возвращаемых значений и события. Это станет таблицей соответствия «метод БПО → вызов Device API».
3. Выяснить правила **описания драйвера и манифеста** (идентификаторы, версии, типы оборудования), как БПО находит и регистрирует драйвер.
4. Выяснить, остаётся ли промежуточный слой на 1С между БПО и компонентой и что он ожидает.
5. Проверить требования к сборке компоненты: SDK Native API, поддерживаемые компиляторы и ОС, ограничения на сторонние библиотеки.
6. Проверить поведение компоненты в **веб-клиенте** и в терминальных сценариях.
7. Принять решение по стеку сервера (Go или TypeScript) и по HTTP-библиотеке компоненты.
8. Решить, одна универсальная компонента на все типы или отдельные сборки по типам.

## 14. Дорожная карта

**Этап 0. Исследование** (раздел 13). Результат: таблица методов ККТ и спецификация манифеста.

**Этап 1. Скелет.**
- Сервер: Device API (сессии, команды), журнал, простейший UI со списком устройств и журналом.
- Компонента-заглушка: подключается в БПО как «Эмулятор ККТ», проходит тест устройства и выполняет один метод через сервер.

## 16. Принципы разработки

- Контракт БПО первичен: имена методов и поведение берутся из требований, а не придумываются.
- Клиент глупый, сервер умный. Любая логика, которую можно держать на сервере, живёт там.
- Всё наблюдаемо: каждый обмен в журнале, каждое срабатывание сценария помечено.
- Состояние моделей воспроизводимо из журнала.
- Конфигурация (профили, сценарии) это файлы, которые можно хранить в git.
- Тесты: модульные для моделей и движка сценариев, интеграционные для Device API, e2e на тестовой конфигурации 1С.
