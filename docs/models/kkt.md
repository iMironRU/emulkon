# Модель ККТ (эмулятор)

Код — `server/internal/models/kkt`. Контракт — [kkt-methods.md](../bpo-requirements/kkt-methods.md)
и [kkt-xml.md](../bpo-requirements/kkt-xml.md). Здесь — как ведёт себя эмулятор: исходное
состояние, проверки, ошибки, управление из Control API.

## Исходное состояние

Новое устройство и устройство после `POST /control/v1/reset`:

- **ККТ уже зарегистрирована** тестовыми данными: ООО «ТЕСТ ЭМУЛКОН» (ЭМУЛЯТОР), ИНН 7700000000,
  СНО `0,1,2,4,5`, ФФД 1.2, признак маркировки. Можно сразу открывать смену и пробивать чеки.
  Сценарий регистрации ФН — через `fiscal: false` и `OperationFN`.
- Заводской номер ККТ (`EMU…`), номер ФН (`9999…`) и регистрационный номер вычисляются из
  идентификатора устройства. У разных устройств они разные, у одного и того же устройства
  после перезапуска сервера — прежние.
- Смена закрыта, последний ФД — 1 (отчёт о регистрации), наличных 0, связь с ОФД есть,
  бумага есть, ширина ленты 42 символа.
- Срок действия ФН — примерно 15 месяцев от создания устройства.

Состояние живёт в памяти сервера: перезапуск — как новое устройство. Восстановление из журнала
(ARCHITECTURE §8) — позже.

## Что проверяется, как на настоящей ККТ

| Операция | Проверки по порядку |
|---|---|
| OpenShift | зарегистрирована, ФН не закрыт и не исчерпан → смена не открыта (иначе 21 или 22) → бумага и крышка, если `PrintRequired` не `false` |
| CloseShift | зарегистрирована, ФН не закрыт → смена открыта (24). **Истёкшую смену закрыть можно** — это выход из ошибки 22 |
| ProcessCheck, ProcessCorrectionCheck | ФН → смена открыта и не старше 24 ч → пакет разбирается → для коррекции есть `CorrectionData` → `OperationType` 1–4 → СНО зарегистрирована → есть фискальные позиции → ставка НДС допустима и сумма НДС есть (кроме `none`) → тип штрихкода → оплачено не меньше суммы чека → безналичных не больше суммы чека → при возврате прихода или расходе в кассе хватает наличных → КМ прошёл RequestKM и ConfirmKM(0) → бумага и крышка (если не `Electronically`) |
| CashInOutcome | ФН → смена → сумма ≠ 0 → для выплаты хватает наличных → бумага |
| OperationFN | ФН не закрыт → смена закрыта (23) → тип 1 — не зарегистрирована (11), типы 2 и 3 — зарегистрирована (10) |
| PrintXReport, PrintTextDocument, PrintCheckCopy | бумага и крышка |

Отклонённая операция ничего не меняет: номер ФД, счётчики и наличные остаются прежними.

**Учёт.** Каждый фискальный документ получает следующий номер ФД:
- отчёт о регистрации, изменении параметров и закрытии ФН;
- открытие и закрытие смены;
- отчёт о текущем состоянии расчётов;
- чек и чек коррекции.

Внесение, выплата, X-отчёт, текстовый документ и копия чека — нефискальные, номера ФД не
получают. Фискальный признак — детерминированный хеш (номер ФН, ФД, время, сумма). Наличные
двигаются по типу операции: приход и возврат расхода — в кассу, возврат прихода и расход — из
кассы. Сдача выдаётся только из наличных.

**Без связи с ОФД** (`ofd_online: false`) каждый новый ФД встаёт в очередь непереданных. Это
видно в `BacklogDocumentsCounter`, `BacklogDocumentFirstNumber` и `BacklogDocumentFirstDateTime`.
Связь вернулась — очередь «передана» и обнулилась.

**Сбой печати после фискализации** (`print_error_after_fiscal`). Чек фискализирован, метод
возвращает `True`, в результате стоит `PrintError="true"`, на ленте документ помечен «сбой печати».

## Маркировка

1. `OpenSessionRegistrationKM` — необязательно: `RequestKM` откроет сессию сам.
2. `RequestKM` — проверяет, что `MarkingCode` — непустой Base64, и запоминает запрос. Локальная
   проверка ФН: `Checking="true"`, `CheckingResult` зависит от `km_result`.
3. `GetProcessingKMResult` — ответ ОИСМ на последний запрос:

   | `km_result` | RequestStatus | ProcessingKMResult |
   |---|---|---|
   | `valid` | 0 | `Result="true" ResultCode="15" StatusInfo="1" HandleCode="0"` |
   | `invalid` | 0 | `Result="false" ResultCode="5" StatusInfo="2" HandleCode="0"` |
   | `suspended` | 0 | `Result="false" ResultCode="15" StatusInfo="3" HandleCode="0"` |
   | `unavailable` | 2 | пусто |
   | любое, пока не прошло `km_delay_ms` | 1 | пусто |

   ResultCode — битовая маска тега 2106: 15 — проверено и корректно, 5 — проверено, результат отрицательный.
   StatusInfo 3 — оборот товара приостановлен (ФФД, табл. 106).

   **Правила по коду** `km_rules` — `[{"title","contains","result"}]`, до 50 штук: ответ берётся из
   первого правила, чья подстрока `contains` входит в раскодированный КМ; результат правила
   фиксируется при `RequestKM`. Код без правила отвечает текущим `km_result` — его можно менять,
   пока касса ждёт ответа ОИСМ.
4. `ConfirmKM(GUID, 0)` — КМ разрешён к продаже; `ConfirmKM(GUID, 1)` — отказ, запрос удаляется.
5. `ProcessCheck` с `MarkingCode` — при `marking_strict` (по умолчанию) КМ должен быть подтверждён,
   иначе ошибка 40. Чек с маркировкой получает `MTNumber`. Сессия КМ закрывается при фискализации.

Блокировки «пока ответ ОИСМ не получен — другие операции невозможны» нет: БПО в режиме
без ожидания подтверждает КМ сразу после первого опроса.

`ConfirmKM(GUID, 0)` после отрицательного ответа ОИСМ модель принимает, как настоящая ККТ: решение
о продаже — за кассой. БПО 3.2.9 этим пользуется: незакрытый запрос она сама подтверждает с `0`
перед следующим `RequestKM` или чеком. Отклонённый код касса должна убрать явно —
`НачатьПодтверждениеКМ` с `Выбытие = Ложь` → `ConfirmKM(GUID, 1)` (прогон tests/1c, «Маркировка»).

## ТС ПИоТ (требования 5.0)

Четыре метода передают данные компоненты ТС ПИоТ (её ставит БПО) через ФН: `PiotSetChallenge`,
`PiotCheckChallenge` — аутентификация, `PiotSetDKMsg`, `PiotGetDKMsg` — защищённый контейнер
(параметры — docs/bpo-requirements/kkt-methods.md). БПО 3.3 включает их, когда в параметрах ККТ
`SupportFNPiot="true"` и в экземпляре оборудования настроен ТС ПИоТ; к ревизии драйвера (4008) не
привязано.

Криптографии ФН у эмулятора нет: ответы — детерминированные тестовые данные с меткой
`EMULKON PIOT TEST` в заголовке t_hdr и `EMULKON-FN-SID-…` вместо токена; ГИС МТ их не примет.
Контейнер `PiotSetDKMsg` = t_hdr + dk_msg1 + хэш, `PiotGetDKMsg` разбирает его обратно.
Проверяются признак `piot`, регистрация ККТ и форма данных (Base64, длины из стандарта) — ошибки 10,
60, 61. Сбои ТС ПИоТ — через сценарии (`method: PiotSetChallenge` и т. д.).

## Коды ошибок

Тексты начинаются с фраз, которые узнаёт БПО (`МенеджерОборудованияКлиент.ЗаполнитьЛокальнуОбработкуОшибок`).

| Код | Текст (начало) | Когда |
|---|---|---|
| 1 | Нет бумаги | `paper: false` и документ печатается |
| 2 | Открыта крышка | `cover_open: true` |
| 10 | ККТ не зарегистрирована | `fiscal: false` |
| 11 | ККТ уже зарегистрирована | повторная регистрация |
| 12 | Фискальный накопитель закрыт | после OperationFN(3) |
| 13 | Исчерпал ресурс КС ФН | `fn_fail: true` |
| 14 | Ресурс хранения ФД исчерпан | `fn_overflow: true` |
| 20 | Кассовая смена не открыта или истекла | операция без смены |
| 21 | Кассовая смена уже открыта | повторное открытие |
| 22 | Смена превысила 24 часа | смена открыта больше 24 ч |
| 23 | Смена открыта: операция возможна только при закрытой смене | OperationFN при открытой смене |
| 24 | Кассовая смена уже закрыта | CloseShift без смены |
| 30 | Неверные данные документа | XML не разбирается, неверный OperationType |
| 31 | Система налогообложения не зарегистрирована в ККТ | `TaxationSystem` вне `TaxationSystems` |
| 32 | Сумма оплаты меньше суммы чека | |
| 33 | Сумма безналичной оплаты больше суммы чека | |
| 34 | Недостаточно наличных в денежном ящике | возврат, расход, выплата |
| 35 | Чек не содержит фискальных позиций | |
| 36 | Неверная ставка или сумма НДС | |
| 37 | Не заданы данные коррекции | |
| 40 | Контрольная марка не проверена | КМ без RequestKM и ConfirmKM(0) |
| 41 | Запрос КМ не найден | ConfirmKM с неизвестным GUID |
| 42 | Нет активного запроса КМ | GetProcessingKMResult без RequestKM |
| 50 | Документ не найден | PrintCheckCopy |
| 51 | Тип штрихкода не поддерживается | не EAN8, EAN13, CODE39, QR |
| 60 | ФН не поддерживает работу с ТС ПИоТ | методы Piot* при `piot: false` |
| 61 | Неверные данные ТС ПИоТ | не Base64 или длина вне стандарта |
| 98 | Неверные параметры вызова | не хватает позиций, неверный тип значения |
| 99 | Метод не поддерживается эмулятором ККТ | |

`GetLastError` возвращает код и текст последней неуспешной операции. Успешная операция их сбрасывает.

## Управление из Control API

`PUT /control/v1/devices/{id}/state` с JSON-объектом. Ключи применяются вместе: при ошибке в
любом не меняется ничего. Каждое изменение пишется в журнал (`control.set_state`).

**Сброс и учёт смен в 1С.** БПО 3.3 ведёт кассовые смены в базе по фискальному устройству и
не шлёт `OpenShift`, пока считает смену открытой; БПО 3.2.9 так не делает. Сброс модели
(`POST /control/v1/reset`, `fiscal`) меняет смену и регистрацию только в эмуляторе: после него
ККТ стоит переподключить в 1С, а открытую в базе смену — закрыть (прогон tests/1c делает это
шагами «переподключить ККТ» и «кассовая смена БПО закрыта в базе»).

| Ключ | Значение | Смысл |
|---|---|---|
| `paper` | bool | бумага есть |
| `cover_open` | bool | крышка открыта |
| `ofd_online` | bool | связь с ОФД; `true` очищает очередь непереданных |
| `fn_error` | bool | признак срочной замены ФН (`FNError`) — только флаг в состоянии |
| `fn_overflow` | bool | память ФН переполнена — фискальные операции отклоняются (14) |
| `fn_fail` | bool | ресурс ФН исчерпан — фискальные операции отклоняются (13) |
| `print_error_after_fiscal` | bool | чек фискализируется, но печать «ломается» (`PrintError`) |
| `fiscal` | bool | `false` — снять регистрацию (и закрыть смену); `true` — зарегистрировать тестовыми данными |
| `cash_balance` | number ≥ 0 | наличные в кассе |
| `shift_opened_hours_ago` | number | сдвинуть время открытия текущей смены (25 — смена истекла) |
| `line_length` | 20–80 | ширина ленты (`GetLineLength`) |
| `taxation_systems` | string | коды СНО через запятую |
| `km_result` | `valid`, `invalid`, `suspended`, `unavailable` | ответ ОИСМ по КМ |
| `km_rules` | `[{"title","contains","result"}]` | ответ ОИСМ по подстроке кода (настройка) |
| `km_delay_ms` | number | задержка ответа ОИСМ |
| `marking_strict` | bool | требовать подтверждённый КМ в чеке |
| `drawer_open` | bool | денежный ящик открыт: открывает `OpenCashDrawer`, закрывают здесь (или сам) |
| `drawer_auto_close_s` | 0–600, `10` | ящик закрывается сам через N секунд; 0 — пока не закроют в карточке |
| `piot` | bool, `false` | ФН работает с ТС ПИоТ: `SupportFNPiot` в `GetDataKKT` и методы Piot* (настройка) |

Пример — «закончилась бумага»:

```bash
curl -X PUT -H "Content-Type: application/json" -d '{"paper":false}' \
  http://127.0.0.1:8737/control/v1/devices/kkt-01/state
```

`GET /control/v1/devices/{id}/prints?limit=20` — лента печати, новые сверху: чеки, отчёты,
нефискальные документы. Все помечены «ЭМУЛЯТОР · НЕ ФИСКАЛЬНЫЙ». Под текстом чека (и его копии) —
настоящий **QR-код ФНС** (`t=…&s=…&fn=…&i=…&fp=…&n=…`, поле `qr` документа: данные и матрица из
`internal/qr`): веб-интерфейс, всплывающее окно и печать трея рисуют его как есть, телефон его
читает. `limit` — до 200: в карточке фильтр «чеки / отчёты» и «Показать ещё». Каждый документ
попадает и в журнал записью `device.print`: на ней работают всплывающие чеки и печать
на принтер в трее ([tray/README.md](../../tray/README.md)).

В веб-UI то же доступно в карточке устройства (вкладка «Устройства» → клик по устройству).
