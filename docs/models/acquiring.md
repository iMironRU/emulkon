# Модель эквайрингового терминала (эмулятор)

Код — `server/internal/models/acquiring`. Контракт — [pos-terminal.md](../bpo-requirements/pos-terminal.md).
Здесь — как ведёт себя эмулятор: исходное состояние, **экран терминала** (карту «прикладывает»
человек), операции, ошибки, управление из Control API.

## Исходное состояние

- Терминал «ТЕСТ-БАНК (ЭМУЛЯТОР)». `TerminalID` (`EMU` + 5 цифр) и `MerchantID` вычисляются из
  идентификатора устройства, как заводской номер у ККТ.
- `TerminalParameters`:
  - `PrintSlipOnTerminal=false` — слип печатает ККТ, как у большинства интегрированных терминалов;
  - `ShortSlip=false`;
  - поддерживаются: выдача наличных (`CashWithdrawal`), частичная отмена (`PartialCancellation`),
    список операций (`ListCardTransactions`), статус операции (`OperationStatus`);
  - не поддерживаются: электронные сертификаты, покупка с зачислением, Consumer-Presented QR.
- Режим карты — **`interactive`**: операция ждёт человека на экране терминала (ниже).
- Связь с банком есть. Пакет операций дня пуст.

Состояние живёт в памяти сервера, как у ККТ.

## Экран терминала: карту «прикладывает» человек

Операции с картой — оплата, возврат, оплата с выдачей наличных, преавторизация, чтение карты
(`GetCardParametrs` без `FromLastOperation`) — в режиме `interactive` **ждут** действия на
экране терминала:

1. Модель открывает запрос: «ОПЛАТА 111.00 ₽ — приложите карту». В журнал пишется
   `device.prompt` (операция, сумма, варианты, срок).
2. Экран видно в двух местах:
   - **трей** на рабочем месте — окно терминала поверх 1С;
   - **веб-интерфейс** — карточка устройства.

   Там кнопки:

   | Действие | Итог |
   |---|---|
   | `card` + `card=mir\|visa\|mastercard\|unionpay\|sbp` | одобрено этой картой (`sbp` — оплата по QR СБП, `AuthorizationType=1`) |
   | `decline` | отказ банка-эмитента (61) |
   | `insufficient` | отказ: недостаточно средств (62) |
   | `wrong_pin` | неверный ПИН-код (63) |
   | `cancel` | клиент отменил операцию на терминале (64) |

3. Ответ уходит `POST /control/v1/devices/{id}/prompt` `{"prompt_id": "…", "action": "card",
   "card": "visa"}`. Модель завершает операцию, в журнал пишется `device.prompt_done`. 1С получает
   результат: команда всё это время ждала.
4. Никто не ответил за `card_timeout_s` (60 с) — отказ 65 «Время ожидания карты истекло».

Ожидание — внутри команды: другие команды этого терминала стоят в очереди, как на настоящем
устройстве. Компонента для операций терминала ждёт ответа сервера до 5 минут: обычный таймаут
в 30 с здесь не подходит.

### Исход по сумме и тестовой карте

Тестировщик управляет терминалом прямо из 1С — суммой или номером карты, без экрана и Control API
(как «магические» суммы платёжных песочниц и порог официального эмулятора 1С). Правила проверяются **до** экрана и `card_mode`:

| Правило | Включается | Исход |
|---|---|---|
| Тестовая карта (`CardNumber` от 1С, пробелы не важны) | всегда | `4000000000000002` — 61, `4000000000009995` — 62, `4000000000000127` — 63 |
| Копейки суммы | `kopeck_rules: true` (по умолчанию выключено: иначе случайная сумма вроде 123,62 даст отказ) | `.61` — 61 отказ банка, `.62` — 62 недостаточно средств, `.63` — 63 неверный ПИН, `.64` — 64 отмена, `.65` — 65 карту не приложили |
| Порог суммы | `decline_above` > 0 | сумма больше порога — 61 отказ банка |

Отказ оформляется как обычно: слип отказа, `device.prompt` не открывается.

Для автотестов экран не нужен — `card_mode`:
- `approve` — сразу одобрено картой `card`;
- `decline` — сразу отказ 61;
- `timeout` — сразу отказ 65.

## Операции

| Метод | Карта | Что проверяется | Итог |
|---|---|---|---|
| Pay | да | связь с банком, `Amount > 0` | операция в пакете дня: RRN, код авторизации, номер чека терминала |
| PayWithCashWithdrawal | да | то же, `AmountCash ≥ 0` | `AmountCash` в ответе и на слипе |
| ReturnPayment | да | `RRNCode` из пакета дня: не отменена (69), сумма возвратов ≤ сумме оплаты (68). RRN нет в пакете — возврат проходит: операция другого дня | новая операция возврата |
| CancelPayment | нет | `RRNCode` — операция дня (67), не отменена (69); `Amount` ≤ суммы (68); частичная отмена — `AmountOriginalTransaction` | отмена; полная — исходная помечается отменённой |
| Authorisation | да | как оплата | блокировка суммы |
| AuthConfirmation | нет | `RRNCode` — преавторизация, не завершена; сумма ≤ заблокированной | списание |
| CancelAuthorisation | нет | `RRNCode` — незавершённая преавторизация | разблокировка |
| EmergencyReversal | нет | есть последняя успешная операция (67) | она отменяется (`reversal`) |
| OperationStatus | нет | — | `Status=1` и параметры операции по `RequestID`, иначе `Status=0` |
| GetOperationByCards | нет | — | `TableOperations` пакета дня |
| Settlement | нет | связь с банком | слип сверки итогов, пакет дня очищается |
| GetCardParametrs | да, если `FromLastOperation=false` | — | маскированный номер, хеш, тип карты, `IsOwnCard=1` |
| PurchaseWithEnrollment, PayCertificate, ReturnCertificate | — | — | 99: терминал этого не умеет (и так объявляет в `TerminalParameters`) |

**RRN** — 12 цифр, **код авторизации** — 6 символов, **номер чека терминала** — по порядку за
день. `UUID` — идентификатор транзакции. `ResultCode=0`, `OperationStatus=0` — всегда заполнены:
БПО читает их через `Число()`.

**Карты — только тестовые**, маскированные: МИР `220070******4417`, VISA `411111******1111`,
MASTERCARD `555555******4444`, UNIONPAY `620000******0000`. Номер карты, переданный из 1С,
сразу маскируется и полностью не хранится. ПИН не запрашивается и не хранится.

**Слип** (`Slip`) — две копии, клиента и кассира, через `[отрезка]`. В шапке
«*** ЭМУЛЯТОР · НЕ БАНКОВСКИЙ ***», ширина 32 символа. При отказе — слип отказа с причиной.
Слип есть и на ленте терминала (`GET …/prints`, журнал `device.print`, всплывающие окна трея).
Если `print_slip_on_terminal=false`, БПО печатает его ещё и на ККТ.

## Коды ошибок

| Код | Текст (начало) | Когда |
|---|---|---|
| 61 | Операция отклонена банком-эмитентом | `decline` |
| 62 | Операция отклонена: недостаточно средств | `insufficient` |
| 63 | Неверный ПИН-код | `wrong_pin` |
| 64 | Операция отменена на терминале | `cancel` |
| 65 | Время ожидания карты истекло | никто не ответил, `card_mode=timeout` |
| 66 | Нет связи с банком | `bank_online: false` |
| 67 | Операция не найдена | RRN нет в пакете дня, аварийно отменять нечего |
| 68 | Сумма превышает сумму исходной операции | отмена, возврат, завершение преавторизации |
| 69 | Операция уже отменена | повторная отмена |
| 98 | Неверные параметры вызова | XML не разбирается, `Amount ≤ 0` |
| 99 | Операция не поддерживается эмулятором терминала | сертификаты, зачисление на карту |

## Управление из Control API

`PUT /control/v1/devices/{id}/state`, как у ККТ (транзакционно, `control.set_state` в журнале):

| Ключ | Значение | Смысл |
|---|---|---|
| `card_mode` | `interactive`, `approve`, `decline`, `timeout` | как «прикладывается» карта |
| `card` | `mir`, `visa`, `mastercard`, `unionpay`, `sbp` | карта для `approve` и выбор по умолчанию на экране |
| `card_timeout_s` | 5–240 | сколько экран ждёт карту |
| `bank_online` | bool | связь с банком |
| `print_slip_on_terminal` | bool | терминал печатает слип сам (`PrintSlipOnTerminal`) |
| `short_slip` | bool | короткий слип (`ShortSlip`) |
| `cash_withdrawal`, `partial_cancellation`, `list_card_transactions` | bool | флаги `TerminalParameters` |
| `kopeck_rules` | bool, `false` | исход по копейкам суммы (выше) |
| `decline_above` | number ≥ 0, `0` | отказ, если сумма больше; 0 — выключено |

`POST /control/v1/devices/{id}/prompt` — ответ на запрос экрана (выше). `409` — запроса с таким
`prompt_id` уже нет: он отвечен или истёк.

В состоянии устройства (`GET /control/v1/devices`) есть `prompt` — текущий запрос экрана —
и `operations` — пакет дня.

## Старая схема (БПО УТ 10.3)

Методы до 4.3 — позиционные, без XML: `ОплатитьПлатежнойКартой` (AuthorizeSales), `ВернутьПлатежПоПлатежнойКарте`
(AuthorizeRefund), `ОтменитьПлатежПоПлатежнойКарте` (AuthorizeVoid), `ПреавторизацияПоПлатежнойКарте`
(AuthorizePreSales), `ОтменитьПреавторизациюПоПлатежнойКарте` (AuthorizeVoidPreSales),
`ЗавершитьПреавторизациюПоПлатежнойКарте` (AuthorizeCompletion): `(0 ИД, 1 НомерКарты, 2 Сумма, 3 НомерЧека,
4 RRN, 5 КодАвторизации, 6 Слип)`. Модель переводит их в `Pay`, `ReturnPayment`, `CancelPayment`,
`Authorisation`, `CancelAuthorisation`, `AuthConfirmation` (`legacy.go`) — экран, отказы, правила копеек,
сценарии и пакет дня общие. `ИтогиДняПоКартам` и `АварийнаяОтменаОперации` в старой и новой схеме одинаковы.
`ПечатьКвитанцийНаТерминале` отвечает компонента: `Ложь` — слипы печатает 1С.
