# Протоколы Эмулкона: Device API и Control API

Формальная спецификация — [`openapi.yaml`](openapi.yaml) (OpenAPI 3.1). Здесь — правила,
которые не выражаются схемой, и то, как ими пользоваться компоненте и автотестам.
Источник требований — [ARCHITECTURE.md](../ARCHITECTURE.md) §5 и §9; контракт драйвера —
«Требования к разработке драйверов подключаемого оборудования» 4.8 и
[bpo-requirements](bpo-requirements/README.md).

Общее: JSON в UTF-8, тело запроса не больше 1 МБ (команда драйвера — до 32 МБ: картинки товаров для весов), время — RFC 3339 в UTC.
Версия протокола — в префиксе пути (`/api/v1`, `/control/v1`); несовместимые
изменения — только через новый префикс.

## 1. Device API (компонента ↔ сервер)

### 1.1. Жизненный цикл компоненты

```
БПО                                   компонента                       сервер
GetInterfaceRevision, GetDescription,
EquipmentParameters, GetAdditionalActions,
SetApplicationInformation, локализация ──► отвечает сама (статические данные)
ConnectEquipment(тип, параметры) ──────► POST /api/v1/sessions ────────► session_id, device_id
                                         ◄── DeviceID (свой дескриптор)
любой другой метод (DeviceID, …) ──────► POST /api/v1/devices/{device_id}/commands (X-Emulkon-Session)
                                         401 session_unknown → новая сессия, повтор с тем же request_id
DisconnectEquipment(DeviceID) ─────────► команда на сервер; сервер закрывает сессию, компонента её забывает
EquipmentTest(тип, параметры) ─────────► пробная сессия → команда → DELETE /api/v1/sessions/{id}
```

- **Методы до подключения компонента обслуживает сама.** БПО вызывает их до
  `ConnectEquipment`, когда адрес сервера ещё неизвестен (он приходит в
  `ConnectionParameters`): ревизия интерфейса, описание драйвера (`DriverDescription`
  с `IsEmulator="true"` и «ЭМУЛЯТОР» в названии — ARCHITECTURE §10), таблица параметров
  настройки (адрес сервера, токен, рабочее место), дополнительные действия (проверка
  обновления драйвера — §1.5), локализация.
  Это статические данные, а не логика: компонента остаётся прокси.
- **`ConnectEquipment`** после открытия сессии компонента тоже передаёт на сервер обычной
  командой, а **`DisconnectEquipment`** — перед тем как забыть сессию. Так подключение
  и отключение видны в журнале и модели. В ответе на `ConnectEquipment` компонента
  подставляет в позицию 0 свой DeviceID.
- **`EquipmentTest`** компонента выполняет как пробное подключение: открывает сессию по
  переданным `ConnectionParameters` и передаёт вызов на сервер. Модель отвечает
  описанием, где явно сказано, что это эмулятор.
- **Сессия.** Компонента открывает её в `ConnectEquipment` и передаёт тип оборудования как
  есть (`KKT`, `ККТ`, `POSTerminal`…). Ответ содержит `device_id` (например `kkt-01`) — все
  дальнейшие вызовы идут к нему — и рекомендуемый таймаут. После переподключения компонента
  попадает на то же устройство с тем же состоянием.
- **Экземпляр в 1С** (ARCHITECTURE §4.3). Компонента передаёт параметры экземпляра из
  `ConnectionParameters`: `instance_id` (`InstanceID`), `instance_name` (`InstanceName`),
  `infobase` (`Infobase`) — все необязательные. Устройство — одно на пару (`instance_id`, тип);
  без `instance_id` — одно на пару (рабочее место, тип), как до 0.7.0. Если в одном процессе 1С
  тот же `instance_id` уже подключён другим экземпляром, компонента добавляет `instance_copy: true`,
  и сервер заводит отдельное устройство с пометкой «копия». `InstanceID` компонента предлагает
  в `EquipmentParameters` как `DefaultValue` — новый GUID при каждом запросе: форма «Настройка»
  БПО сохраняет его в карточке экземпляра.
- **DeviceID для 1С** компонента выдаёт свой (дескриптор подключения): одна компонента
  может держать несколько устройств, в том числе на разных серверах. В параметрах команд
  он уходит на сервер как есть — сервер его не интерпретирует, устройство определяет путь.
- **Сессии живут в памяти сервера.** После перезапуска сервера или 24 ч простоя
  (`EMULKON_SESSION_IDLE_TTL`) команда получит `401 session_unknown` — компонента молча
  открывает новую сессию и повторяет команду. Для 1С это не видно.
- **Закрытие сессии.** Сервер закрывает сессию сам после `DisconnectEquipment` — и в повторе
  с тем же `request_id` из новой сессии (ответ потерялся), так что отключённые устройства
  не висят в «Сессиях». Пробную сессию «Теста устройства» компонента закрывает
  `DELETE /api/v1/sessions/{id}` (неизвестная сессия — тоже `200`). В журнале —
  `session.closed` с `reason`: `DisconnectEquipment` или `client`.
- **Токен устройства** (`device_token`) передаётся только при открытии сессии. Дальше
  сессию идентифицирует заголовок `X-Emulkon-Session`. Если на сервере не задан
  `EMULKON_DEVICE_TOKEN`, принимается любой токен (открытый режим, только для локальной работы).
- **Токен рабочего места** (ARCHITECTURE §10). Выдаётся в UI («Рабочие места») или
  `POST /control/v1/workstations/{id}/token`, виден один раз, на сервере хранится SHA-256.
  В драйвере он вписывается в тот же параметр «Токен устройства». Допуск при открытии сессии:
  1. токен рабочего места — место берётся из токена; `workstation_id` можно не задавать.
     Если он задан явно и называет другое место — `401 bad_token`. Имя компьютера, которое
     компонента подставляет сама (`workstation_auto: true`), токен заменяет;
  2. месту выдан токен, а пришли без него или с другим — `401 bad_token`, даже в открытом режиме;
  3. иначе — общий `EMULKON_DEVICE_TOKEN`, если задан, или открытый режим.

  Закрыть сервер целиком: задать `EMULKON_DEVICE_TOKEN` и не раздавать его — подключатся
  только места с выданными токенами. Перевыпуск отменяет прежний токен, отзыв снимает защиту
  места; открытые сессии в обоих случаях живут до конца. В журнале `session.open` — способ
  допуска `auth` (`workstation`, `server`, `open`) и `workstation_requested`, если место
  назвал токен; сам токен не пишется.

### 1.2. Команды и идемпотентность

Каждый вызов метода драйвера из 1С — одна команда. Параметры **позиционные**, как в
Native API: компонента передаёт массив всех параметров (входных и выходных) и записывает
обратно массив из ответа — так 1С получает выходные параметры.

```json
POST /api/v1/devices/kkt-01/commands
X-Emulkon-Session: s_…

{ "request_id": "6f1c…", "method": "ProcessCheck",
  "params": ["h1", false, "<CheckPackage …/>", ""], "client_ts": "2026-10-08T09:00:00Z" }

→ 200
{ "request_id": "6f1c…", "result": true,
  "params": ["h1", false, "<CheckPackage …/>", "<DocumentOutputParameters …/>"],
  "error_code": 0, "error_text": "" }
```

- `method` — английское имя метода из требований (компонента регистрирует в 1С оба имени,
  русское и английское, и на сервер шлёт английское).
- `params` — значения Native API: STRING → строка, LONG и DOUBLE → число, BOOL → булево,
  пустое — `null`. Вложенных структур нет: таблицы передаются XML-строками (раздел 1 требований).
  Числа сервер хранит без потери точности.
- `result` — возвращаемое значение метода: булево (BOOL), целое (LONG — например
  `GetInterfaceRevision`, `GetLastError`) или `null`.
- Ответный `params` всегда той же длины, что и запрос.
- `error_code`, `error_text` — последняя ошибка устройства. Компонента запоминает их из
  ответа и сама отвечает на `GetLastError`. Так ошибка доступна и тогда, когда до сервера
  уже не достучаться, а при сбое связи компонента подставляет свой код (900 — нет связи).
  Сервер тоже понимает `GetLastError` как обычную команду: он помнит последнюю ошибку
  каждого устройства, успешный вызов её сбрасывает. Это для автотестов, работающих по HTTP.

Правила:

1. `request_id` генерирует компонента (UUID) — один на вызов метода из 1С.
2. **Повтор с тем же `request_id` возвращает тот же ответ, метод второй раз не выполняется.**
   Если первый запрос ещё выполняется, повтор дождётся его результата. Так закрывается
   сценарий «ответ пришёл после таймаута»: компонента при таймауте или обрыве повторяет
   запрос с тем же `request_id` и получает результат первого выполнения, а не второе
   списание денег.
3. Тот же `request_id` с другим методом или параметрами — `409 request_id_conflict` (ошибка компоненты).
4. Ответы хранятся 15 минут, но не больше 10 000 последних на сервер. `POST /control/v1/reset` их очищает.
5. Команды одного устройства выполняются **строго по очереди**, как на настоящем железе.
   Начатая команда доводится до конца, даже если компонента отключилась, — её результат
   нужен для повтора.

### 1.3. Ошибки: устройство или транспорт

| Что случилось | Как выглядит | Что делает компонента |
|---|---|---|
| Ошибка **устройства** (нет бумаги, отказ банка, смена > 24 ч) | `200`, `result: false`, `error_code`, `error_text` | Возвращает в 1С как ошибку драйвера |
| Нет / неизвестна сессия | `401 session_unknown` | Новая сессия, повтор команды с тем же `request_id` |
| Неверный токен устройства | `401 bad_token` | Ошибка подключения в 1С, без повторов |
| Сессия от другого устройства | `403 wrong_device` | Ошибка компоненты (баг), без повторов |
| Некорректный запрос | `400 bad_request`, `400 unknown_equipment_type` | Ошибка компоненты, без повторов |
| Повтор `request_id` с другим содержимым | `409 request_id_conflict` | Ошибка компоненты, без повторов |
| Журнал недоступен | `503 unavailable` | Команда **не выполнялась**; можно повторить |
| Таймаут, обрыв соединения | — | Повтор с тем же `request_id` (экспоненциальная пауза) |

Тело транспортной ошибки: `{"error": {"code": "…", "message": "…"}}`.

### 1.4. События устройства (сервер → компонента → 1С)

Сканер, считыватель карт, весы, дисплей покупателя отдают данные в 1С **внешними событиями**
(`ExternalEvent(Who, What, Data)`, требования, раздел 3.8). Компонента после `ConnectEquipment`
держит поток SSE:

`GET /api/v1/devices/{device_id}/events` с `X-Emulkon-Session`:

```
event: ready
data: {}

id: dlzhspvu1hs4.1
event: device
data: {"event_id":"dlzhspvu1hs4.1","time":"…","name":"Barcode","data":"4600000000008"}

: ping
```

- `name` — bstrWhat из требований (Barcode, TracksData, Weighting, OnClick, …), `data` — bstrData.
  Компонента поднимает `ExternalEvent(<свой DeviceID>, name, data)`; Who — DeviceID, который она
  вернула 1С из `ConnectEquipment`.
- **Курсор** — `id` последнего полученного события в `Last-Event-ID` при переподключении: сервер
  отдаёт пропущенное (буфер — 200 последних событий устройства). Без курсора — только новые события,
  чтобы старые сканы не попали в 1С. Курсор вида «эпоха.номер»: после перезапуска сервера устройство
  создаётся заново, и курсор прежней эпохи значит «всё, что накопилось».
- Пинг — раз в 15 с; он же продлевает сессию. Истекла сессия — поток закрывается, компонента
  открывает новую. Тишина дольше 45 с — компонента переподключается сама.
- Каждое событие — запись журнала `direction: event`, `method` — имя события, в `payload` — число
  слушающих компонент (`listeners`). В карточке устройства — `event_listeners`.

### 1.5. Самообновление драйвера и загрузки

Сервер раздаёт дистрибутив из каталогов загрузок (`-downloads`, `EMULKON_DOWNLOADS_DIR`, значение реестра
`DownloadsDir` — через `;`; по умолчанию `1C\driver` и `setup` установки рядом с `bin\`, иначе `downloads` рядом с
программой). Файл с одним именем берётся из первого каталога, где он есть. Версия — в имени файла:

| Файл | Что это |
|---|---|
| `EmulkonDriver_<версия>.zip` | пакет драйвера для БПО со всеми типами (INFO.XML, MANIFEST.XML, DLL Windows x64 и x86, `.so` Linux x64 — если собран) |
| `EmulkonDriver_<версия>_<тип>.zip` | тот же пакет с одним типом в INFO.XML (`kkt`, `acquiring`, …): сервер собирает его из общего, на диске его нет |
| `EmulkonDriver_<версия>_win64.dll`, `…_win32.dll`, `…_lin64.so` | драйвер для самообновления: Windows x64 и x86, Linux x64 |
| `EmulkonSetup_<версия>.exe` | установщик Эмулкона для Windows |

Посторонние файлы каталога не раздаются. Всё открыто **без токенов**: файлы не секретны,
а кассе нужно скачать драйвер до любых настроек.

| Метод | Назначение |
|---|---|
| `GET /downloads` | страница «Поддержка и загрузки»: что поддерживается, скачивание, как установить в БПО |
| `GET /downloads/{файл}` | файл; каждое скачивание — запись `download` в журнале (рабочее место — из `X-Emulkon-Workstation`) |
| `GET /api/v1/downloads` | каталог: самые новые файлы каждого вида с размером и SHA-256, поддержка оборудования; у типа с драйвером — `package`, пакет под этот тип |
| `GET /api/v1/driver/update?version=&arch=&os=` | есть ли драйвер новее для архитектуры `x86_64` или `i386` и ОС `windows` (по умолчанию) или `linux` |

**Как обновляется драйвер.**
1. Компонента открывает сессию с `driver_version`, `driver_arch` и `driver_os` (`windows`, `linux`; без него —
   `windows`, как у драйверов до 0.9.0). Если в каталоге загрузок есть драйвер этой ОС и архитектуры новее,
   ответ содержит `driver_update`: `{version, url, size, sha256}`.
   В журнале у `session.open` будет поле `driver_update`.
2. Компонента скачивает DLL в фоне, если в настройке не выключено «Обновлять драйвер автоматически»
   (`AutoUpdate`). Операция 1С скачивания не ждёт. Размер и SHA-256 сверяются до того, как файл
   получит рабочее имя: `%LOCALAPPDATA%\Emulkon\driver\<версия>\EmulkonDriver_win64.dll`; на Linux —
   `$XDG_CACHE_HOME/emulkon/driver/<версия>/libEmulkonDriver_lin64.so` (по умолчанию `~/.cache/…`).
3. При следующей загрузке компоненты (перезапуск 1С) её экспорты переадресуются в самую новую
   DLL из кэша. Переустанавливать драйвер в БПО не нужно. Битая DLL пропускается.
   `EMULKON_DRIVER_NO_UPDATE=1` в окружении 1С выключает переадресацию.
4. Вручную — дополнительное действие БПО **«Проверить обновление драйвера»** (`CheckUpdate`)
   в форме настройки экземпляра: спрашивает `/api/v1/driver/update` и сразу скачивает.
   Параметры подключения БПО дополнительным действиям не передаёт, поэтому адрес сервера
   берётся из последнего подключения или теста устройства. `EquipmentTest` тоже сообщает
   о новой версии в описании результата.

Пакет драйвера в базе 1С при этом остаётся прежним. Новые рабочие места получают из базы
старую версию и обновляются при первом подключении. Обновить сам пакет — карточка драйвера →
«Обновить драйвер» → архив со страницы загрузок. DLL в пакете называются с версией
(`EmulkonDriver_0_6_1_win64.dll`): тонкий клиент помнит установленные компоненты по имени файла
и DLL с прежним именем не переустанавливает (component/README.md). В сборках не для выпуска к имени добавлено
начало SHA-256 библиотеки (`EmulkonDriver_0_9_0_85f8f906_win64.dll`), чтобы и новая сборка той же версии ставилась (#10).


## 2. Control API (UI и автотесты ↔ сервер)

Авторизация — `Authorization: Bearer <EMULKON_CONTROL_TOKEN>`; токен отдельный от
токена устройств. Если токен не задан — API открыт (сервер предупреждает в логе и в UI).

| Метод | Назначение | Статус |
|---|---|---|
| `GET /control/v1/info` | версия, режимы токенов, типы устройств, сводка журнала | есть |
| `GET /control/v1/devices` | устройства и состояние моделей | есть |
| `GET /control/v1/sessions` | рабочие места и сессии | есть |
| `GET /control/v1/journal` | чтение журнала с фильтрами, выгрузка JSONL | есть |
| `GET /control/v1/journal/stream` | живой поток журнала (SSE) | есть |
| `POST /control/v1/reset` | сброс состояния моделей перед тестом | есть |
| `PUT /control/v1/devices/{id}/state` | задать состояние: бумага, крышка, ФН, ОФД, 24 ч смены, ответ ОИСМ, вес на весах, бумага принтера… (ключи — [models/kkt.md](models/kkt.md), [models/acquiring.md](models/acquiring.md), [models/scales.md](models/scales.md), [models/printers.md](models/printers.md)) | есть (ККТ, терминал, весы, принтеры) |
| `GET /control/v1/devices/{id}/prints` | лента печати: чеки, отчёты, нефискальные документы, слипы, этикетки | есть (ККТ, терминал, весы с печатью этикеток, принтеры) |
| `POST /control/v1/devices/{id}/prompt` | ответ с экрана устройства: «приложить карту», отказ, отмена ([models/acquiring.md](models/acquiring.md)), вес на весах ([models/scales.md](models/scales.md)); `409 prompt_gone` — запрос уже закрыт | есть (терминал, весы) |
| `POST /control/v1/devices/{id}/actions/{name}` | действие человека на самом устройстве: напечатать этикетку на весах (`print_label`), картинка товара (`image`), отсканировать (`scan`), провести карту (`swipe`), нажать на дисплей (`click`), отобрать товар на ТСД (`collect`), положить RFID-метку (`add_tag`)… — у каждой модели свои, docs/models/; `404` — у устройства нет такого действия | есть |
| `POST /control/v1/devices/{id}/events` | событие устройства для 1С как есть: `{"name", "data"}`, имя — из требований (Barcode, TracksData, DriverError, …); сканы и карты удобнее действиями `scan`, `swipe` | есть |
| `PATCH /control/v1/devices/{id}` | подпись и заметка устройства `{"alias", "note"}` (§2.3) | есть |
| `DELETE /control/v1/devices/{id}` | удалить устройство руками; его сессии закрываются (§2.3) | есть |
| `POST /control/v1/devices/{id}/settings/reset` | вернуть устройству настройки его класса (§2.3) | есть |
| `GET /control/v1/workstations` | рабочие места: подпись, базы, устройства, сессии (§2.3) | есть |
| `PATCH /control/v1/workstations/{id}` | подпись и заметка рабочего места (§2.3) | есть |
| `PUT /control/v1/workstations/{id}/printers` | принтеры Windows рабочего места — сообщает трей (§2.3) | есть |
| `POST/DELETE /control/v1/workstations/{id}/token` | выдать (перевыпустить) или отозвать токен рабочего места (§1.1); неизвестное место заводится | есть |
| `POST /control/v1/devices/{id}/reprint` | напечатать последний документ ещё раз — запись `device.reprint` для трея (§2.3) | есть |
| `GET /control/v1/types` | классы устройств: схема ключей состояния и настройки по умолчанию (§2.3) | есть |
| `PUT /control/v1/types/{key}/defaults` | настройки класса по умолчанию (§2.3) | есть |
| `GET/POST /control/v1/scenarios`, `PUT/DELETE …/{id}` | сценарии сбоев: правила «условие → действие» (§2.4) | есть |

### 2.0. Экран устройства, который ждёт человека

Некоторые операции устройства ждут человека: на эквайринговом терминале — «приложите карту»,
на весах в режиме `weight_mode=ask` — «положите товар» с полем веса. Команда драйвера в это
время не отвечает, а в журнал пишется `device.prompt`. Его payload — запрос экрана:

- `prompt_id`, `operation`, `title`, `text`, `amount`, `amount_cash`;
- кнопки `actions[]` — `{id, title, kind}`;
- карты `cards[]` и карта по умолчанию `default_card` (терминал);
- поле ввода `input` — `{label, unit, value, min, max, step}` (весы: «Вес, кг»);
- срок `deadline`.

Тот же запрос есть в состоянии устройства (`state.prompt`).

Ответ — `POST /control/v1/devices/{id}/prompt` `{"prompt_id", "action", "card", "value"}`:
`card` — для кнопки `card`, `value` — число в пределах `input` для любой кнопки, кроме
`cancel`. Так отвечают веб-интерфейс (карточка устройства) и трей (окно устройства). Итог
пишется записью `device.prompt_done`: `{prompt_id, operation, result: {action, card, value, text}}`.
Сразу за ней идёт ответ команды (`out`).

**Действия на устройстве.** Кроме ответа на запрос, человек может что-то сделать на самом
устройстве — например, напечатать этикетку на весах. Это `POST …/actions/{name}` с аргументами
в теле (JSON-объект). Действие идёт в общей очереди команд устройства; в журнал пишутся
`control.action` и напечатанное (`device.print`) — так этикетка попадает в трей. Действия
моделей — в [models/](models/).

Трей подписан на `method=device.print,device.reprint,device.keyboard,device.prompt,device.prompt_done` своего
рабочего места: в фильтре журнала `method` — одно имя или несколько через запятую. Показывать и
печатать ли документ, решает сервер по настройке устройства (`output` в записи, §2.3).
`device.keyboard` `{text, suffix, delay_ms}` — ввести код с клавиатуры в активное окно: сканер или
считыватель в клавиатурном режиме (docs/models/input.md).

### 2.1. Журнал

Запись журнала (ARCHITECTURE §8) плюс служебные поля:

```json
{
  "seq": 15,
  "ts": "2026-10-08T06:36:22.809Z",
  "correlation_id": "live-check-1",
  "session_id": "s_0f7c…",
  "workstation_id": "KASSA-01",
  "device_id": "kkt-01",
  "direction": "out",
  "method": "PrintXReport",
  "payload": { "request_id": "live-check-1", "result": true, "params": ["h1", "<InputParameters …/>"], "error_code": 0, "error_text": "" },
  "latency_ms": 0,
  "applied_rules": [],
  "replay": false
}
```

- `seq` — монотонный номер, переживает перезапуск; это курсор для чтения и потока.
- `direction`: `in` — команда от компоненты, `out` — ответ, `event` — событие к компоненте (§1.4),
  `system` — служебное: `session.open` (в т.ч. отказы, с полем `payload.rejected`),
  `session.closed`, `session.expired`, `control.reset`, `control.set_state`, `control.device_meta` и
  `control.workstation_meta` (подпись, заметка, вывод — что изменено) и **`device.print`** — документ,
  «напечатанный» устройством во время команды. В `payload` — документ целиком (`kind`,
  `number`, `time`, `lines`…; у пакета этикеток принтера этикеток ещё `layout` — разметка и
  значения полей для просмотра), `correlation_id` = `request_id` команды. Пишется между `in` и
  `out`. На этом потоке работает трей:
  `/control/v1/journal/stream?method=device.print&workstation_id=…`. Документ, напечатанный
  действием на устройстве (этикетка с весов), пишется после `control.action`, без `correlation_id`.
- `correlation_id` = `request_id`: связывает `in` и `out` одной команды.
- `replay: true` — повтор запроса с тем же `request_id`, отдан сохранённый ответ.
- Токены в журнал не пишутся.
- Строковый параметр команды длиннее 128 КБ (картинки товаров) в журнале обрезается:
  начало и пометка `…[в журнале обрезано: N байт]`. Устройство получает его целиком.

Чтение — `GET /control/v1/journal?device_id=kkt-01&direction=out&limit=100`: последние
записи по фильтру. Назад — `before_seq=<seq первой записи>`. Выгрузка — `format=jsonl`.

Поток — `GET /control/v1/journal/stream?tail=200` (или `after_seq=N`, или заголовок
`Last-Event-ID`): дочитка, затем `event: ready`, затем новые записи. Встроенный
`EventSource` браузера не умеет заголовки, поэтому UI читает поток через `fetch`.

### 2.3. Учёт устройств: экземпляры, рабочие места, классы

Решение — ARCHITECTURE §4.3. Устройства, рабочие места и настройки хранятся в
`<каталог данных>/registry.json` и переживают перезапуск сервера.

**Устройство** в `GET /control/v1/devices` кроме прежних полей содержит:

| Поле | Что это |
|---|---|
| `instance_id`, `instance_name`, `infobase` | экземпляр в 1С — как их передала компонента (§1.1) |
| `keyed_by` | `instance` — устройство по `instance_id`; `workstation` — по рабочему месту («не настроено») |
| `copy` | экземпляр подключился копией уже подключённого (тот же `instance_id`) |
| `alias`, `note` | подпись и заметка администратора |
| `settings` | сохранённые настройки устройства (ключ → значение) |
| `online` | есть сессия, активная за последние 5 минут |

**Настройки и состояние.** У каждого класса есть схема ключей `PUT …/state`
(`GET /control/v1/types`): поле `{key, title, kind, options, min, max, hint, setting}`.
`kind` — `bool`, `number`, `int`, `enum`, `string`, `json`. `setting: true` — настройка: она
сохраняется у устройства, её можно задать классу по умолчанию. Остальные ключи — состояние
и сбои (бумага, вес, связь): меняются, но не сохраняются. `PUT …/state` сохраняет настройки
из изменения сам.

Новое устройство получает настройки своего класса. `POST /control/v1/reset` возвращает модели
в исходное состояние и снова применяет настройки каждого устройства. `…/settings/reset` делает
то же для одного устройства, но с настройками класса — свои настройки устройства забываются.

**Рабочее место** (`GET /control/v1/workstations`): `workstation_id`, `alias`, `note`,
`first_seen`, `last_seen`, `infobases` (базы его устройств), `devices` (идентификаторы),
`sessions` (открытых).

**Класс** (`GET /control/v1/types`): тип оборудования, `schema`, `defaults` — настройки по
умолчанию. `PUT /control/v1/types/{key}/defaults` заменяет их целиком; значения проверяет сама
модель, неверный ключ или значение — `400`. На уже существующие устройства не влияет.

**Вывод документов** (ARCHITECTURE §4.3) — у устройств, которые печатают (ККТ, принтеры,
терминал, весы с этикетками), поле `output` в `GET …/devices`:
`{screen, printer, printer_name, kinds}`. `screen` — показывать документ на экране кассы
(по умолчанию да), `printer` — печатать на принтер Windows (нет), `printer_name` — пусто —
принтер по умолчанию, `kinds` — группы документов для печати (`GET /control/v1/types` →
`output_kinds` класса; по умолчанию чеки, коррекции, копии). Меняется
`PATCH /control/v1/devices/{id}` `{"output": {…}}` и хранится в реестре.

Сервер добавляет в payload записи `device.print` решение: `output: {screen, print, printer}`.
`POST /control/v1/devices/{id}/reprint` — напечатать последний документ ленты ещё раз: запись
`device.reprint` (payload как у `device.print`, `output.print = true`, `screen = false`).
Трей подписан и на неё.

**Принтеры рабочего места.** Трей сообщает принтеры своего компьютера:
`PUT /control/v1/workstations/{id}/printers` `{"printers": [...], "default": "..."}`. Они есть
в `GET …/workstations` (`printers`, `default_printer`) — из них карточка предлагает выбор.

Удаляет устройство только `DELETE` — руками.

### 2.4. Сценарии сбоев

Правило (ARCHITECTURE §7):

```json
{
  "name": "Нет бумаги на третьем чеке",
  "enabled": true,
  "match": {"device": "kkt-01", "method": "ProcessCheck", "nth_call": 3},
  "action": {"type": "error", "error_code": 3, "error_text": "Нет бумаги", "delay_ms": 1000},
  "limit": 0
}
```

`match` — все условия вместе, пустое — любое: `device`, `type` (класс), `workstation`, `method`
(несколько — через запятую, без учёта регистра), `param` `{index, equals, contains}` — параметр
вызова по номеру (XML параметров — подстрокой, например `Amount="999`), `nth_call` — только N-й
подходящий вызов, `every` — каждый N-й, `probability` — доля срабатываний (0 — всегда).
`limit` — не больше N срабатываний.

| `action.type` | Что происходит |
|---|---|
| `error` | ответ `result: false` с `error_code`/`error_text`; модель не вызывается; GetLastError вернёт эту ошибку |
| `delay` | ждать `delay_ms`, затем выполнить как обычно (у `error` `delay_ms` — задержка перед ошибкой) |
| `drop` | выполнить и оборвать соединение без ответа; повтор с тем же `request_id` получает сохранённый результат |
| `late` | выполнить и ответить через `delay_ms` — после таймаута компоненты |
| `set_state` | применить `state` к модели (как `PUT …/state`), затем выполнить |
| `emit_event` | отправить `event` `{name, data}` в 1С, затем выполнить |

Срабатывает несколько правил: задержки складываются, состояния и события копятся, ответ
(`error` или `drop`) — от первого правила по порядку. Правило вычисляется один раз на первое
выполнение: повтор с тем же `request_id` правила не трогает. Сработавшие правила — в
`applied_rules` записей `in` и `out` журнала; в ответе Control API у правила `seen` (подходящих
вызовов) и `fired` (срабатываний). `POST /control/v1/reset` обнуляет счётчики. Сам сервер ничего не удаляет; давно не
подключавшиеся устройства интерфейс помечает по `last_seen`.

## 3. Хранение журнала

Каталог `$EMULKON_DATA_DIR/journal`, файлы `journal-NNNNNN.jsonl`, новый файл —
при превышении `EMULKON_JOURNAL_MAX_FILE_MB` (32 МБ), хранится `EMULKON_JOURNAL_MAX_FILES`
(8) последних. Файлы не переименовываются (на Windows открытый читателем файл
переименовать нельзя). Недописанная при аварии строка пропускается при чтении.
